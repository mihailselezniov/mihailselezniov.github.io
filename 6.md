## 📋 Пошаговая расшифровка плана

### 1. `Parallel Seq Scan on sales`
- **Что делает:** последовательно читает всю таблицу `sales`, используя два параллельных рабочих процесса (`Workers Planned: 2`).
- **Фильтр:** `EXTRACT(month FROM sale_date) = '12'` и `EXTRACT(year FROM sale_date) = '2025'`. Из-за применения функций к колонке `sale_date` **невозможно использовать индекс**, даже если бы он был. Фильтр вычисляется для каждой строки.
- **Оценка:** cost `0.00..15686.33`, ожидается всего 10 строк, удовлетворяющих фильтру (оптимизатор не знает реальной селективности). На практике декабрьских записей может быть намного больше, и тогда последовательное сканирование становится очень дорогим.

### 2. `Index Scan using products_pkey on products`
- **Что делает:** по `product_id`, полученному из `sales`, ищет соответствующую строку в таблице `products` через первичный ключ.
- **Метод соединения:** Nested Loop – для каждой строки из `sales` (внешний цикл) выполняется индексный поиск в `products`.
- **Оценка:** на каждую строку `sales` тратится `0.29..2.06`. При большом количестве декабрьских продаж это приводит к многократным обращениям к индексу и таблице `products`.

### 3. `Sort`
- **Ключ сортировки:** `products.category_id`.
- **Цель:** подготовить строки к групповой агрегации (`GroupAggregate`), которая требует отсортированных данных по ключу группировки.
- **Оценка:** сортировка ожидаемых 10 строк практически бесплатна, но при реальном большом наборе станет более затратной.

### 4. `Partial GroupAggregate`
- **Что делает:** выполняет частичную группировку в каждом параллельном воркере независимо. Суммирует `amount` по `category_id` на своём подмножестве данных.
- **Результат:** каждый воркер выдаёт набор частичных агрегатов (по одному на каждую встреченную категорию).

### 5. `Gather Merge`
- **Что делает:** собирает частичные результаты от обоих воркеров, сохраняя сортировку по `category_id`. Это необходимо, чтобы итоговая агрегация (`Finalize GroupAggregate`) могла объединить частичные суммы по одинаковым категориям, которые должны идти подряд.
- **Параллелизм:** `Workers Planned: 2` – используется два фоновых процесса для сканирования и агрегации.

### 6. `Finalize GroupAggregate`
- **Что делает:** завершает агрегацию – для каждой категории суммирует частичные суммы, полученные от воркеров через `Gather Merge`. Так как данные уже отсортированы, агрегация выполняется эффективно, без дополнительной сортировки.

### 7. `Limit`
- **Что делает:** возвращает первые 10 строк после итоговой агрегации. Важно: `LIMIT` применяется **после** группировки, поэтому не может сократить объём обрабатываемых данных на ранних стадиях. Оптимизатор вынужден сначала вычислить суммы по всем категориям, а потом отбросить лишние.

## ❌ Основные проблемы плана

1. **Неиндексируемый фильтр**  
   `EXTRACT(MONTH FROM sale_date) = 12 AND EXTRACT(YEAR FROM sale_date) = 2025` вычисляется для каждой строки. Нельзя использовать индекс по `sale_date`. Отсюда – дорогое последовательное сканирование всей таблицы.

2. **Nested Loop и множество обращений к products**  
   Если в декабре много продаж, для каждой из них будет индексный поиск в `products`. Это вызывает лавину случайных чтений.

3. **LIMIT после GROUP BY**  
   Нет возможности остановиться раньше, потому что сначала нужны все агрегаты. При большом количестве категорий группировка обрабатывает полный объём данных.

4. **Параллелизм помогает, но не кардинально**  
   Parallel Seq Scan ускоряет чтение, но не устраняет фундаментальной неэффективности фильтрации и соединения.

## ⏱️ Оценка стоимости
Общая стоимость `16707.15..16708.34` – это условные единицы. Верхняя граница у `Limit` низкая, потому что оптимизатор думает, что будет всего ~25 строк после агрегации, и лимит отсечёт 10 из них. На самом деле, если декабрьских продаж сотни тысяч, стоимость будет значительно выше, и план деградирует.

## 📌 Сравнение с предыдущим планом

### 1. Фильтр стал SARGable
Условие `sale_date >= '2025-12-01' AND sale_date < '2026-01-01'` теперь работает с колонкой напрямую, без функции `EXTRACT`. Это позволяет оптимизатору:
- Использовать статистику распределения значений `sale_date`, чтобы **реалистично оценить количество строк** (11 527 вместо прежних 10).
- Применить индекс по `sale_date`, если бы он существовал, но так как индекса нет, остаётся последовательное сканирование. Однако возросшая оценка кардинальности кардинально влияет на выбор стратегии соединения.

### 2. Nested Loop → Hash Join
Когда оптимизатор ожидал всего **10 строк** из `sales`, одиночные индексные поиски в `products` для каждой строки были выгодны (мало обращений).  
При прогнозе **11 527 строк** стоимость `Nested Loop` резко возрастает, потому что потребуется десятки тысяч индексных доступов к `products`.  
Вместо этого оптимизатор выбирает **Hash Join**: один раз полностью читает `products` (10 000 строк, `Seq Scan`), строит хеш-таблицу, а затем для каждой строки из `sales` выполняет быструю проверку хеша. Это существенно эффективнее для больших объёмов.

### 3. Partial GroupAggregate → Partial HashAggregate
- Прежний `Nested Loop` выдавал строки в порядке, определяемом сканированием `sales` и последующим индексным поиском – это не гарантировало сортировку по `category_id`. Однако для `GroupAggregate` нужна была сортировка, которую обеспечивал отдельный `Sort` перед агрегацией.
- Новый `Hash Join` возвращает строки в произвольном порядке. Оптимизатор решил использовать **HashAggregate**, который не требует сортировки входных данных – группировка происходит через хеширование. Это эффективнее, чем сортировка большого набора строк (ожидаемых 11 527) перед агрегацией.
- Но так как `HashAggregate` выдаёт несортированные результаты, а для окончательной агрегации (`Finalize GroupAggregate`) через `Gather Merge` требуются данные, отсортированные по `category_id`, появляется **дополнительный `Sort`** после частичной агрегации (у каждого воркера свои группы сортируются перед слиянием). Это плата за использование хеширования.

### 4. Снижение общей стоимости
Несмотря на появление явной сортировки, стоимость упала с ~16 707 до ~15 052 единиц. Причина:
- `Hash Join` обходится дешевле, чем множество индексных доступов в `Nested Loop` для большого числа строк.
- `HashAggregate` эффективнее сортировки миллионов строк (в данном случае 11 тысяч).

**Стало:**  
Простой `HashAggregate` сразу считает итоговые суммы по `category_id`. Без параллелизма отпала необходимость в частичных агрегатах и их объединении.

```sql
CREATE MATERIALIZED VIEW sales_monthly_by_category AS
SELECT
    p.category_id,
    DATE_TRUNC('month', s.sale_date) AS month,
    SUM(s.amount) AS total_amount
FROM sales s
JOIN products p ON s.product_id = p.product_id
GROUP BY p.category_id, DATE_TRUNC('month', s.sale_date);

-- Индекс для быстрого поиска конкретного месяца
CREATE INDEX ON sales_monthly_by_category (month, category_id);

-- Если надо обновить представление
REFRESH MATERIALIZED VIEW sales_monthly_by_category;
```

EXPLAIN SELECT category_id, total_amount

- фильтровать миллионы строк по `sale_date`,
- соединять с `products` для получения `category_id`,
- выполнять `GROUP BY` и `SUM`.

### 2. Простой `Index Scan` вместо сложного плана
Благодаря индексу `(month, category_id)` на материализованном представлении, условие `month = '2025-12-01'` отрабатывает мгновенно. Планировщик выбирает:

- **Динамический запрос** всегда возвращает актуальные данные на момент выполнения.
- **Материализованное представление** – снимок на момент последнего `REFRESH`. Если продажи добавляются непрерывно, данные устаревают до следующего обновления. При необходимости актуальности в реальном времени нужно либо часто обновлять MV, либо использовать инкрементальные агрегаты.

Партиция — это обычная таблица в базе, в которую попадают строки, удовлетворяющие её диапазону/условию. Каждая партиция — это отдельная физическая таблица/отношение с собственными файлами хранения и индексами.

**Основные преимущества:**

- Быстрая фильтрация (partition pruning). Планировщик читает только те партиции, которые соответствуют условию по ключу партиции (в вашем случае — sale_date). В примере QUERY будет сканировать только sales_2025_12, а не всю историческую таблицу — существенно меньше I/O и CPU.

- Уменьшение объёма сканируемых индексов. Индексы создаются на каждой партиции, они меньше по размеру ➞ быстрее поиск/скан/восстановление видимости.

- Быстрая ежемесячная/годовая очистка данных. Удалить старые данные можно мгновенно и дешёво через DROP PARTITION или TRUNCATE PARTITION, вместо массового DELETE (нет WAL‑нагрузки и bloat).

- Эффективное обслуживание (VACUUM/ANALYZE/REINDEX) по частям. Обслуживание можно выполнять только на нужных партициях, снижая время и блокировки.

- Параллелизм и partition‑wise операции. Планировщик может выполнять partition‑wise join/aggregate и параллельно обрабатывать партиции, что даёт ускорение для больших наборов данных.

**Минусы:**

- Повышенная сложность схемы и админства: надо планировать диапазоны/называть партиции, создавать новые партиции.

- Накладные расходы при очень большом количестве партиций (thousands) — планировщик и метаданные могут страдать.

- Партиционирование эффективно только если запросы фильтруют по ключу партиции; если фильтр отсутствует, выигрыш будет невелик.

- Нужно управлять индексами на каждой партиции (дополнительные операции при создании партиций).

## 🛠️ Улучшаем производительность #5

#### Переписать запрос с предварительной агрегацией по `product_id`
Если в `sales_2025_12` много строк на один товар, лучше сначала агрегировать продажи по товару, а потом джойнить `products`. Это может сильно помочь, если строк в продажах много, а уникальных `product_id` относительно мало.

```sql
SELECT p.category_id, SUM(t.total_amount) AS total_amount
FROM (
    SELECT product_id, SUM(amount) AS total_amount
    FROM sales_2025_12
    GROUP BY product_id
) t
JOIN products p USING (product_id)
GROUP BY p.category_id
ORDER BY total_amount DESC
LIMIT 10;
```

Вместо соединения миллионов продаж с products вы соединяете гораздо меньший набор (по числу `distinct product_id`), поэтому `hash/merge‑join` строит меньшую хэш‑таблицу и требует меньше памяти/CPU.

```sql
CREATE INDEX CONCURRENTLY ON sales_2025_12 (product_id) INCLUDE (amount);
```

Если на партиции сделать индекс по `product_id` (и `amount`), первичная агрегация может быть более эффективной. Но мы уже похожее делали, поэтому не будем акцентировать на этом моменте.

## 🛠️ Улучшаем производительность #6

💡**Денормализация — максимальный выигрыш!**
Если добавить `category_id` прямо в таблицу `sales` (и в секции), запрос перестанет нуждаться в `JOIN`:

```sql
ALTER TABLE sales ADD COLUMN category_id INT;
-- Заполнение, поддержка через триггер или на уровне приложения.
-- А сейчас нарушим это и нам просто надо переложить данный category_id из product.

UPDATE sales
SET category_id = p.category_id
FROM products p
WHERE sales.product_id = p.product_id
  AND (sales.category_id IS DISTINCT FROM p.category_id);
```

Вот теперь финально не забываем про `INDEX`:

```sql
CREATE INDEX idx_sales_partitioned_cover
    ON sales (sale_date, category_id) INCLUDE (amount);
```

FROM sales s
WHERE s.sale_date >= '2025-12-01'
  AND s.sale_date <  '2026-01-01'

ORDER BY SUM(amount) DESC
